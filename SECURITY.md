# Security

Please report vulnerabilities privately: on GitHub open **Security → Report a vulnerability** in this repository. Don't open a public issue for them.

## What the bot holds and how it treats it

- **Bot token, the API keys set in `.env` (YouTube, Anthropic, the site's ingest token), the mail-worker token** live only in environment variables; the keys you connect from the chat live in the database (next item). Every log line passes a redacting formatter (`bot/redact.py`): the bot token, keys in a URL query, the `li_at` cookie, a password in a URL and every secret value the bot was started with are masked in the message and the traceback alike. The httpx logger is kept at WARNING on top: at INFO it prints every Bot API URL.
- **Instagram access token** (`/igtoken`), **LinkedIn `li_at` cookie** (`/setcookie`), the **watchdog address** (⏱ Watchdog — whoever has it can ping in the bot's name) and the **reputation report's three read-only keys** (🔎 Reputation — the Search Console service-account key, the Yandex.Webmaster OAuth token and the Cloudflare token) the **YouTube API key** when it was sent in the chat (🔌 Connections → «➕ YouTube»), the **Claude API key** of the comment check (💬 Channel comments), and the **app password of the separate mailbox** and the **mail-worker token** when they were sent in the chat (✉️ Security emails) are stored in the SQLite DB on your volume (`_SECRET_SETTINGS` in `bot/db.py`). The message carrying any of them is deleted from the chat right away, the weekly backup the bot sends to the chat is made without them, none of them reaches a screen or a log line, and `/restore` never overwrites a live one with a stale copy. The Instagram token belongs to your own Meta app; how long it lives depends on how Meta issued it (Instagram-login tokens live 60 days) — if it leaks, revoke it there: remove the app's Instagram Tester role or the app itself.
- **Follower history, profile baselines, checklist answers, security events and alerts held back by quiet hours or `/mute`** are in the same DB; the held alerts are live state and are left out of the backup. Nothing leaves it except the counts you choose to push to your own site (`SITE_INGEST_URL`), the status lines to your own TofsDevOps (its address set in ⏱ Watchdog or `HEALTHCHECK_URL`), the comments sent to Claude when that check is on, and the weekly backup to your own chat.
- **Least privilege by design.** The bot reads only public data of your own accounts through official APIs where they exist (Telegram, YouTube, Instagram); it never asks for a password, and the hygiene checklist is your own marks. LinkedIn has no API for a personal profile's followers, so its number is scraped with your cookie or typed in by hand.
- **Security emails** reach the bot through a separate mailbox or your own mail-worker. From the mailbox the bot reads only mail its provider vouched for — the topmost `Authentication-Results` (the one the provider adds) has `dkim=pass` for the domain of `From` — and only from the known security senders; anything else, a forged «security alert» included, stays unread and raises nothing. The app password opens the whole mailbox, so it is meant for a box made only for the bot, never your main one. The mail-worker accepts mail from the senders you list (`ALLOWED_SENDERS`) and drops the rest. A key or a password sent in the chat passes through Telegram's servers before the bot deletes the message: that is why the keys are read-only, the mailbox is a separate one and the Claude key belongs in a Workspace with a spend limit. Links quoted from a mail or a changed profile description are defanged (`hxxps://evil[.]example`), as are other people's display names and invite-link names, and link previews are off, so an alert never carries a clickable scam link.
- **Comments of the channel** (with `ANTHROPIC_API_KEY`): the text and picture of every new comment in the discussion group go to the Claude API without the author's id, name or @username; flagged comments are kept in the DB as a text excerpt with the author's id and name, so a card button can act on them later (for 180 days); a comment the model called fine keeps only the author's id and the verdict (30 days), for «first message in the group» and the count in `/comments`. At most three comments are classified at once and at most `COMMENTS_DAILY_LIMIT` a day, so a spam wave is bounded in API calls and in cost. The bot never deletes or bans on its own — every action is a tap on a card; it needs the group admin rights to delete messages and ban members, nothing more. Nothing from a group or a channel ever reaches the owner-only handlers, so the bot does not answer strangers there.
- **Life of the channel** (the bot as a channel admin): every join and leave is kept in the DB with the subscriber's id and name and the invite link's name it came through — for 90 days, then dropped — every post with its reaction counts; nothing else about a subscriber, and nothing of it leaves your server (the weekly backup carries it to your own chat). Switched off in `/modules`, nothing is recorded. The bot needs no right beyond being an admin: Telegram sends these updates to every admin bot.
- **Access**: every command and button checks that the user is the owner — the first `/start` after the deploy (kept in the DB), or `ADMIN_CHAT_ID` when it is set, which wins; everyone else is refused. Before an owner exists the bot sends no message; collection, the site push and the watchdog ping already run. The token is the only thing that lets anyone find a fresh bot, so send it `/start` right after it starts.
- **Supply chain**: dependencies are pinned, `pip-audit` and `npm audit` run in CI, Dependabot keeps them current, and the bot reports known vulnerabilities (OSV) in its packages on Sundays. The container drops root after handing the data directory to `appuser`.
